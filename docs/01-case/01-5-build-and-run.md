# 01-5 · 编译命令、全部产物、上机验证

前三讲我们把"应该是什么样"推导完了。这一讲做三件事：

1. 把案例真的编译出来、在 GPU 上跑出 `PASS`；
2. 一次性生成后面每一讲都要用到的全部中间产物；
3. 把命令行的坑一次讲清楚——**尤其是那些"不报错但结果不对"的坑**。

## 一、先跑起来：两条路径都要跑

```bash
bash tools/build-and-run.sh
```

这个脚本做两件事：用 `nvcc` 编一遍，用 `clang++` 编一遍，然后都在本机 GPU 上跑。
输出是：

```
===== [1] nvcc -arch=sm_89 -O3 =====
GEMM: M=256 N=128 K=64  (sm_89, mma.m16n8k16)
[v1 manual  ] max |D - ref| = 4.29153e-06   -> PASS
[v2 ldmatrix] max |D - ref| = 4.29153e-06   -> PASS
nvcc 路径 rc=0

===== [2] clang++ 作为 CUDA 编译器 (host+device) =====
GEMM: M=256 N=128 K=64  (sm_89, mma.m16n8k16)
[v1 manual  ] max |D - ref| = 4.29153e-06   -> PASS
[v2 ldmatrix] max |D - ref| = 4.29153e-06   -> PASS
clang 路径 rc=0
```

看到这四个 `PASS`，我们就可以放心往下走了。

顺便解释一下那个 `4.29153e-06` 是怎么来的：它是在 host 侧算的
`max |D - ref|`，其中 `ref` 是同一个 CPU 上跑的 fp32 三重循环。

**为什么不是 0？** 因为输入是 f16（只有 10 位尾数），累加是 f32。
f16 的机器 epsilon 大约是 `9.8e-4`，累加 64 项之后误差落在 `1e-6` 量级是合理的。

**怎么判断"误差是合理的"？** 记住这个经验：

> **布局错了，误差不会停在 1e-6，而是直接蹦到个位数。**

我们在开发 v2 的时候见过一次 `max |D - ref| = 13.9497`——那是因为 `ldmatrix` 的 `.trans`
配错了布局，转置转了两遍。所以后面你看到误差"数量级不对"，第一反应应该是"**fragment 布局错了**"，
而不是"精度不够"。

## 二、一次生成全部中间产物

```bash
bash tools/dump-all.sh
```

它会在 `dumps/` 下生成一整套文件。这套文件就是后面每一讲的素材。
先认一遍清单（第 1 列是文件名前缀，你可以在 `dumps/` 里对应着找）：

| 产物 | 文件 | 用什么命令生成的 |
| --- | --- | --- |
| 设备端 IR（未优化） | `01-device-O0.ll` | `clang++ -x cuda ... --cuda-device-only -O0 -S -emit-llvm` |
| 设备端 IR（优化后） | `02-device-O2.ll` | 同上，`-O2` |
| PTX（clang 出） | `03-clang-O2.ptx` | `clang++ ... --cuda-device-only -O2 -S`（不带 `-emit-llvm`） |
| PTX（nvcc 出，对照） | `04-nvcc-O3.ptx` | `nvcc -arch=sm_89 -O3 -ptx` |
| cubin + 资源用量 | `05-clang.cubin`、`05-ptxas-verbose.txt` | `ptxas -arch=sm_89 -v` |
| SASS | `06-sass-cuobjdump.txt`、`07-sass-nvdisasm.txt` | `cuobjdump -sass` / `nvdisasm -c -hex` |
| 寄存器/共享内存占用 | `08-res-usage.txt` | `cuobjdump -res-usage` |
| 指令选择后的 MIR | `09-mir-after-isel.mir` | `llc -stop-after=finalize-isel` |
| 编码前的 MIR | `10-mir-after-regalloc.mir` | `llc -stop-after=nvptx-prolog-epilog` |
| 驱动完整日志 | `11-clang-verbose.log` | `clang++ ... -v` |
| host 端 IR | `12-host-O0.ll` | `clang++ ... --cuda-host-only -O0 -S -emit-llvm` |

**这张表背不下来没关系，但要记住它的结构：**

```
IR（O0 / O2） → PTX（clang / nvcc 两条） → cubin → SASS（两种视图）
                    ↑
                中间还有 MIR（ISel 后 / 编码前）
```

## 三、一条命令一条命令地看

脚本里其实就几条命令，我们拆开讲。先定义两个变量，后面所有命令都用它们：

```bash
CUDA=/usr/local/cuda-12.8
CFLAGS="--cuda-path=$CUDA --cuda-gpu-arch=sm_89"
```

### 1）设备端 IR（我们要反复用）

```bash
clang++ -x cuda $CFLAGS --cuda-device-only -O2 -S -emit-llvm \
        -o dumps/02-device-O2.ll code/tc_mma.cu
```

三个关键开关：

| 开关 | 作用 |
| --- | --- |
| `-x cuda` | 让 clang 走 CUDA 前端（认 `__global__`、`__shared__`、`<<<>>>`） |
| `--cuda-device-only` | 只编译设备端，不做 host 编译、不链接 |
| `-S -emit-llvm` | 输出 LLVM IR 文本，而不是 PTX |

### 2）PTX

```bash
clang++ -x cuda $CFLAGS --cuda-device-only -O2 -S \
        -o dumps/03-clang-O2.ptx code/tc_mma.cu
```

**注意 `-S` 后面没有 `-emit-llvm`**，所以这里出的是 PTX 文本。
这是整条链路上唯一"由 LLVM 生成、但要交给别家工具处理"的产物。

### 3）PTX → cubin → SASS

```bash
ptxas -arch=sm_89 -v -o dumps/05-clang.cubin dumps/03-clang-O2.ptx
cuobjdump -sass dumps/05-clang.cubin > dumps/06-sass-cuobjdump.txt
nvdisasm -c -hex dumps/05-clang.cubin > dumps/07-sass-nvdisasm.txt
```

**从这一行开始，你已经离开 LLVM 的世界了。** `ptxas` 是 NVIDIA 的汇编器，
它有自己的寄存器分配器和调度器。第 8 部分会专门讲它做了什么。

### 4）停在中间某一站看 MIR

```bash
llc -mtriple=nvptx64-nvidia-cuda -mcpu=sm_89 -O2 \
    -stop-after=finalize-isel -o dumps/09-mir-after-isel.mir dumps/02-device-O2.ll
```

`-stop-after=<pass 名>` 是读后端时最有用的工具：**它让流水线停在某一站，把当时的
Machine IR 打印成文本。** 第 6 部分我们会靠它看指令选择的结果。

这里有个版本坑要提醒你：**`prologepilog` 这个名字在 NVPTX 上已经不成立了**。
NVPTX 禁用了通用的 `PrologEpilogInserter`，改用自己实现的 `NVPTX Prolog Epilog Pass`，
所以你得写：

```bash
llc ... -stop-after=nvptx-prolog-epilog ...   # 对
llc ... -stop-after=prologepilog ...          # 错：LLVM ERROR: "prologepilog" pass is not registered
```

## 四、命令行的坑：三个"看起来没问题"的写法

这一节是我强烈建议你读的部分，因为 CUDA + clang 的命令在网上流传得很乱。

### 坑 1：`-arch=sm_89` 是 nvcc 的写法，不是 clang 的

```bash
$ clang++ -x cuda ... -arch=sm_89 ...
clang++: error: unknown argument '-arch=sm_89'; did you mean '-march=sm_89'?
```

这个是**硬报错**（exit code 1，不产出文件），反而好办。正确写法是 `--cuda-gpu-arch=sm_89`。
clang 也接受 `--offload-arch=sm_89`，两者产出的 `target-cpu` 完全一样。

### 坑 2：忘了写 `--cuda-gpu-arch`，它会默默给你编 sm_52

这个坑才阴险。**不写架构，clang 不报错**：

```bash
$ clang++ -x cuda --cuda-path=$CUDA --cuda-device-only -O2 -S -o t.ptx t.cu
$ head -6 t.ptx
//
// Generated by LLVM NVPTX Back-End
//

.version 8.7
.target sm_52          ← 不是你要的 sm_89！
```

你要一直读到 PTX 才会发现不对。所以**每次写 clang 命令都检查一遍 `--cuda-gpu-arch`**。

### 坑 3：`--no-cuda-version-check` 在你这个版本上是不需要的

网上很多 CUDA + clang 的教程会让你加 `--no-cuda-version-check`。那是因为老版本 clang
只认到 CUDA 12.3，遇到 12.8 会警告。本机这版 clang 直接认识 12.8，加了没坏处，
但**它掩盖了"版本不匹配"这件事**——如果哪天你真的用了比 clang 新的 CUDA，
宁可由它警告你，也别一直带着这个开关。

## 五、验证一下"产物链是连着的"

做完前面几步，你可以用一条命令确认这条链确实是连起来的：

```bash
$ ls -l dumps/ | awk '{print $5, $9}' | head -14
```

典型输出（大小会随版本略有变化）：

```
34123 01-device-O0.ll
14072 02-device-O2.ll
 8437 03-clang-O2.ptx
16127 04-nvcc-O3.ptx
11168 05-clang.cubin
10592 05-nvcc.cubin
666   05-ptxas-verbose.txt
```

这四行数字里藏着一个很值得注意的现象：

- **PTX 差了一倍**：clang 出的 `03-clang-O2.ptx` 只有 8.4 KB，nvcc 出的 `04-nvcc-O3.ptx` 有 16.1 KB；
- **但 cubin 几乎一样大**：11.2 KB vs 10.6 KB。

为什么会这样？因为 **nvcc 在 PTX 层就把 k 循环展开了**（所以它的 PTX 又长又"手工"），
而 clang 把循环原样交给 ptxas，让 ptxas 自己在生成 SASS 时展开。
**两条路走到最后，机器码的规模收敛到了一起。**

这个现象本身就是很好的教学点，第 7 部分（PTX 对照）和第 8 部分（SASS）都会回到它。

## 六、小结

1. 这门课的所有结论都建立在"能跑出 PASS"之上。**先跑 `build-and-run.sh`，再谈别的。**
2. `dumps/` 里那套文件是后面每一讲的素材，它的结构是
   `IR → PTX → cubin → SASS`，中间还夹着两个 MIR。
3. 命令行三个坑：`-arch` 是 nvcc 的、忘写架构会静默变 sm_52、
   `--no-cuda-version-check` 不需要。

到这里第 1 部分就结束了。你现在手里有：一个能跑的案例、三张 fragment 布局表、
一整套中间产物。**这就是"靶子"。**

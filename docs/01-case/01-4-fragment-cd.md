# 01-4 · C/D fragment 与整张拼图

前两讲把 A 和 B 拆完了。这一讲收掉最后两个 fragment，然后把三张表拼成一张大图——
这张大图就是后面所有章节的"地图"。

## 一、C 和 D 是同一个布局

先说一个可能让你意外的事实：**`mma.sync` 里 C 和 D 的 fragment 布局完全一样**，
因为它们本来就是同一个东西的两个角色。

回忆 `mma` 干的事：

```
D = A × B + C
```

`C` 是累加器的输入，`D` 是累加器的输出。它们的形状一样（都是 16×8 的 f32）、
布局一样（同一套公式），区别只是"读"还是"写"。

所以我们的代码里直接让它们共用一组寄存器：

```cpp
mma_m16n8k16(c, a, b, c);   // 同一个 c 既当输入又当输出
```

这不是省事，而是**标准做法**：`mma` 支持原地累加，硬件层面 `d` 和 `c` 指向同一组寄存器。
你在 PTX 里会看到同一个寄存器名出现在第 1 个和第 4 个操作数上：

```
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
    {%r33,%r34,%r35,%r36},      <- D
    {%r22,%r23,%r24,%r25},      <- A
    {%r20,%r21},                <- B
    {%r33,%r34,%r35,%r36};      <- C（和 D 是同一组）
```

## 二、C/D 的账和布局

```
C/D 的元素数 = 16 行 × 8 列 = 128 个 f32
warp 线程数 = 32
每个线程 = 128 / 32 = 4 个 f32 = 4 个寄存器
```

布局公式：

| 寄存器 | 元素 |
| --- | --- |
| `c[0]` | `D[gid][2*tig]` |
| `c[1]` | `D[gid][2*tig+1]` |
| `c[2]` | `D[gid+8][2*tig]` |
| `c[3]` | `D[gid+8][2*tig+1]` |

画成图：

```
                    n = 0..7
              ┌──────────────────────────────────────┐
   row 0..7   │  c[0] = D[gid][2*tig]                │   同一行的相邻两列
              │  c[1] = D[gid][2*tig+1]              │   （在内存里相邻）
              ├──────────────────────────────────────┤
   row 8..15  │  c[2] = D[gid+8][2*tig]              │
              │  c[3] = D[gid+8][2*tig+1]            │
              └──────────────────────────────────────┘
```

和 A、B 对照一下：

- A：寄存器里两个 half 是**同一行相邻的 K**；
- B：寄存器里两个 half 是**同一列相邻的 K**；
- C/D：`c[0]` 和 `c[1]` 是**同一行相邻的 N**（注意是 N，不是 K）。

**又是"相邻"，这次是 N 方向相邻。** 因为 D 在内存里就是 row-major 的 f32，
所以 `c[0]`、`c[1]` 这两个数在内存里相差 4 字节，**可以成对写出去**。

## 三、写回的代码就是照着这张表写的

```cpp
float *pd0 = D + (tile_m + c_r0) * N + tile_n + c_c;   // c_r0 = gid,    c_c = 2*tig
float *pd1 = D + (tile_m + c_r1) * N + tile_n + c_c;   // c_r1 = gid+8
pd0[0] = c[0];
pd0[1] = c[1];
pd1[0] = c[2];
pd1[1] = c[3];
```

读这段代码的时候注意两件事：

1. `c_c = tig * 2`，所以 `pd0[0]` 和 `pd0[1]` 是**相邻的两个 float**——
   在内存里正好差 4 字节；
2. `pd0` 和 `pd1` 差了 `8 * N` 个 float（因为 `c_r1 = gid + 8`）。

到了 SASS 里，这会变成这样四条存储：

```
st.global.b32   [%rd31], %r33 ;
st.global.b32   [%rd31+4], %r34 ;
st.global.b32   [%rd35], %r35 ;
st.global.b32   [%rd35+4], %r36 ;
```

**看那个 `+4`**：它就是 `c[0]` 和 `c[1]` 相邻这件事在机器码里的样子。
第 8 部分我们读 SASS 时，会用这四条 `st.global` 反过来验证 C fragment 的布局——
这是一个很好的"闭环"：从公式推出来，再到机器码里确认。

## 四、整张拼图：三个 fragment 放在一起

把 A、B、C/D 三张表并排放在一张图里，这是这门课最重要的一张图：

```
                       ┌─────────────────── B (16×8, f16) ───────────────────┐
                       │  每线程 2 个 .b32                                     │
                       │  b[0] = {B[2t][gid],   B[2t+1][gid]}                 │
                       │  b[1] = {B[2t+8][gid], B[2t+9][gid]}                 │
                       └──────────────────────────────────────────────────────┘
                                     ▲
   ┌──── A (16×16, f16) ────┐        │
   │ 每线程 4 个 .b32        │        │
   │  a[0] = {A[gid][2t],   A[gid][2t+1]}     （左上）│
   │  a[1] = {A[gid+8][2t], A[gid+8][2t+1]}   （左下）│
   │  a[2] = {A[gid][2t+8], A[gid][2t+9]}     （右上）│
   │  a[3] = {A[gid+8][2t+8], A[gid+8][2t+9]} （右下）│
   └─────────────────────────┘        │
                                      ▼
                       ┌────────── mma.sync m16n8k16 ──────────┐
                       │   D = A × B + C                        │
                       └────────────────────────────────────────┘
                                      │
                                      ▼
                       ┌──────── C/D (16×8, f32) ────────┐
                       │  每线程 4 个 .f32                │
                       │  c[0] = D[gid][2t]              │
                       │  c[1] = D[gid][2t+1]            │

                       │  c[3] = D[gid+8][2t+1]          │
                       └─────────────────────────────────┘
```

## 五、自检：这些数字对不对得上

一张布局表最容易出的错是"多算/少算了元素"。我们可以用一个简单的方法自检——
**从两个方向数一遍，看能不能对上**：

```
每个线程拿到的元素：
  A: 4 个寄存器 × 2 个 half = 8 个
  B: 2 个寄存器 × 2 个 half = 4 个
  C: 4 个寄存器 × 1 个 f32  = 4 个

32 个线程合起来：
  A: 32 × 8 = 256  = 16 × 16 ✓
  B: 32 × 4 = 128  = 16 × 8  ✓
  C: 32 × 4 = 128  = 16 × 8  ✓
```

两边对得上，说明你没有漏掉或重复分配元素。**反过来，如果你在推自己的布局时数字对不上，
那一定有地方错了**——这个方法比死记硬背靠谱。

第二个自检方法是查"覆盖性"：把 32 个线程的坐标全列出来，看看有没有哪个元素被两个线程
同时拿到。这个练习我在 01-2 的动手题里留给你了。

## 六、一个必须说清楚的边界：以上都是 "m16n8k16" 的布局

这里我要提醒一句，**这三讲的公式是"这一条指令"的布局，不是 Tensor Core 的通用规律**。

PTX ISA 里每一条 `mma` 形状都有自己的 fragment 布局表，比如：

| 指令 | A 的每个线程寄存器数 |
| --- | --- |
| `m16n8k8.f16` | 2 |
| `m16n8k16.f16` | 4（我们的） |
| `m16n8k16.bf16` | 4 |
| `m16n8k8.tf32` | 4（但元素是 tf32，一个寄存器装 1 个） |
| `m16n8k4.tf32` | 2 |

**形状变了，账就要重算。** 但你会算：先数总元素数、除以 32、除以每寄存器装几个，
再去手册上查"哪几个元素进哪个寄存器"。这套方法是你自己的，不会过时。

## 七、小结

1. C 和 D 是同一个布局（`D = A×B + C` 的累加形式），我们的代码里它们共用一组寄存器。
2. C/D 每线程 4 个 `.f32`，`c[0]`/`c[1]` 是**同一行相邻的两列**——
   在内存里相邻，所以写回是四条 `st.global.b32`，两条一对（相差 4 字节）。
3. 三个 fragment 合起来的"账"必须两头对得上：**总元素数 = 32 × 每线程元素数**。
   这个自检方法可以推广到任何一条 mma 形状。

到这里，案例的理论部分就完备了：我们知道每个线程手里有什么、这些东西从哪来、算完写到哪去。
下一讲我们把它真的编译出来、跑起来，看看这条链路能不能通。

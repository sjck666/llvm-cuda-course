# 01-1 · 为什么是这样一个案例

这一讲不写代码，只讲"为什么这个案例长这样"。但我保证这不是废话——**你这个案例选得对不对，
决定了后面十讲能不能讲清楚**。所以我把我当初的取舍过程原样讲给你听。

## 一、先明确目标：我们要看清什么

要设计一个"适合解剖的案例"，我先写下三条硬性要求：

1. **它必须真的能跑**，而且能在 GPU 上验证数值正确。
   理由很实在：编译器相关的东西特别容易"看起来对了"。IR 你读懂了、PTX 你读懂了，
   结果 kernel 跑出来是错的——这种事我遇到过太多次。**一个能在 GPU 上对拍数值的案例，
   是所有结论的最终裁判。**

2. **它必须覆盖完整的 Tensor Core 数据通路**：load → shared memory → fragment → mma → store。
   如果只写最简单的"从 global 直接 load 然后 mma"，那 shared memory 的地址空间、
   `cp.async` 的异步语义、`ldmatrix` 的转置分发，这些全都讲不到。

3. **它必须小到你能在纸上算账。** 每一行 IR、每一条 SASS，我都要能对回源码里的某一个变量。

## 二、第一个决定：用哪条 mma 指令

CUDA 里手写 Tensor Core，你面对的第一件事是选指令形状。Ada 这一代（sm_89）上，
f16 输入的 `mma.sync` 有好几种：

```
mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32      ← 早期形状，K=8
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32     ← 我们选的
mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32   ← bf16 变体
mma.sync.aligned.m16n8k16.row.col.f32.tf32.tf32.f32   ← tf32 变体
```

我选 `m16n8k16` 的 f16 版本，理由有三条，都是"为了讲得清"：

**第一，它是最经典的一条。** sm_80 引入，sm_89 完整支持，PTX ISA 手册里对它的 fragment
定义画得最全，测试用例最多。你在网上找到的资料，八成也是拿它当例子。

**第二，它的寄存器数量刚好能算清账。** 一条 `m16n8k16` 指令的四个 fragment：

```
A：16×16 个 f16    每线程 4 个 .b32（每个 .b32 装 2 个 f16）
B：16×8  个 f16    每线程 2 个 .b32
C/D：16×8 个 f32   每线程 4 个 .f32
```

一共 10 个寄存器。这个数字小到你可以一眼记住，又大到足够覆盖"多个寄存器拼一个操作数"
这个关键概念。k8 的版本每线程只有 2 个 A 寄存器，账太简单，讲不出味道。

**第三，它的 SASS 形态很标准。** 对应的机器指令是 `HMMA.16816.F32`，
第 8 部分我们可以把它的四个操作数一个一个拆开讲，而且它周围的数据流——
`LDSM` 装 fragment、`PRMT` 打包 half、`LDG` 读 global——全是这一代硬件的标准动作。

## 三、第二个决定：写两个 kernel，而不是一个

这是这个案例最"刻意"的地方。文件里有两个 kernel：

```cpp
mma_tc_manual     // v1: 手动从 global memory 组装 fragment，完全不碰 shared memory
mma_tc_ldmatrix   // v2: cp.async 把 tile 搬进 shared memory，再用 ldmatrix 装 fragment
```

它们算的是同一个矩阵乘，结果也相同（误差都是 `4.29e-06`）。为什么不写一个？

因为**这两条路径在编译链路里长得完全不一样**，而这门课要讲的恰恰是"链路"：

**v1 的 IR 是这样的**：一堆普通的 `load i32` / `load i16`，加一条内联汇编的 `mma`。
你看到的每一行 IR 都能对回源码里的一次内存访问。**这是讲前端和 IR 的最好的素材**——
干净、没有魔法。

**v2 的 IR 里出现了什么**：`addrspace(3)`（共享内存）、`cp.async`（异步拷贝）、
`ldmatrix`（矩阵加载）、`llvm.nvvm.barrier.cta.sync.aligned.all`（同步）。
**"地址空间"和"同步"这两件事，只有 v2 才能讲清楚**——而这两件事恰好是 CUDA 前端
在 IR 里留下的最深的两个脚印。

再往后看：

- 第 7 部分讲 PTX 时，v1 给你看"4 条 `ld.global.nc.b32` 怎么装 A"，
  v2 给你看"一条 `LDSM` 怎么装 A"，一对比你就明白 `ldmatrix` 存在的意义；
- 第 8 部分讲 SASS 时，v2 里能看到 `LDGSTS`（cp.async 的真身）、
  `BAR.SYNC`（同步）、`LDSM`（矩阵加载）和 `HMMA` 挤在一个循环里，
  这是理解"软件流水"的最好现场；
- v1 的 SASS 则干净得多（56 条 `LDG`、7 个 `HMMA` 站点），适合第一次读 SASS 时不被打断。

**一句话：v1 用来讲"前端和 IR"，v2 用来讲"地址空间、同步和后端"。**
两个都要，而且要在同一个文件里，这样才能随时对照。

## 四、第三个决定：M/N/K 取多少

案例里 `M = 256`、`N = 128`、`K = 64`。这三个数字也是挑过的：

**必须是 mma 形状的整数倍。** `M % 16 == 0`、`N % 8 == 0`、`K % 16 == 0`。
这样一来，任何一次 fragment 加载都不需要做边界判断，IR 干净、SASS 短、
你读的时候不会被打断。如果你写过真实项目，你会知道真实项目里到处是
`if (row < M)` 这种尾巴处理——那是工程问题，不是编译器问题，我们把它排除掉。

**K = 64 让 k 循环正好 4 圈。** 每圈前进 16（一条 mma 吃 16 深度的 K），所以 64/16 = 4。
为什么在意"4 圈"？因为第 4 部分讲循环展开时，你会看到"能不能展开、展开成几条"
这件事有多微妙——**4 是个好数字，它小到编译器愿意完全展开，又大到展开之后
SASS 里的结构看得清楚。**

**矩阵小到可以在 CPU 上跑一份 fp32 参考实现做对拍。** `256×128` 的输出，
CPU 三重循环算一遍是毫秒级的。这一步非常重要：它就是前面说的"最终裁判"。

于是 launch 配置也很简单：

```
grid  = dim3(N/8, M/16) = (16, 16)
block = dim3(32)                    // 一个 warp，一个 block
```

**一个 block 就是一个 warp，一个 warp 算一个 16×8 的 tile。** 慢，但是账目清楚：
你不用担心"哪个 warp 干了什么"，所有代码都是"一个 warp 里 32 个线程怎么分工"。

## 五、第四个决定：不用 CUTLASS / CuTe

这个决定值得解释，因为很多人会问"为什么不直接看 CUTLASS"。

CUTLASS 是优秀的库，但它是**另一个抽象层**。如果你拿 CUTLASS 的 kernel 去 dump IR，
你看到的会是"CUTLASS 模板实例化的结果 + LLVM 的 lowering"混在一起。
当你想问"这条 IR 为什么长这样"的时候，你没法判断这是 LLVM 干的，
还是 CUTLASS 的模板元编程在编译期算出来的。

**手写 60 行 fragment 代码，换来的是每一行 IR 都能对回源码。** 这个交换在这门课里非常值。

## 六、案例的整体形状

把上面的决定画成图：

```
                  ┌─────────────────────────────────────────┐
   A (256×64)     │  v1: 每个线程直接从 global 读自己那份     │     D (256×128)
   B (64×128)     │      a[0..3] / b[0..1] / c[0..3]        │
      f16         │      → 一条 mma                          │      f32
                  ├─────────────────────────────────────────┤
                  │  v2: cp.async 搬 16×16 / 16×8 的 tile    │
                  │      → ldmatrix 装 fragment → mma        │
                  └─────────────────────────────────────────┘
```

两条路径后面会反复出现，请记住它们的名字：**v1（manual）** 和 **v2（ldmatrix）**。

## 七、小结与预告

1. 案例的目标不是"高性能"，是"**可验证 + 可看清**"：能跑、能对拍、每一行都能对回源码。
2. 选 `m16n8k16` 是为了寄存器账好算（A/B/C/D = 4/2/4 个寄存器）；
   选两个 kernel 是为了同时讲清"干净路径"和"shared memory + 同步路径"。
3. `M/N/K = 256/128/64` 让边界处理彻底消失，让 k 循环正好 4 圈——
   **把工程噪音排除掉，剩下的才是编译器行为。**

下一讲开始，我们进入这个案例的核心：**fragment 布局**。这是整门课最该背下来的一张表，
因为后面读 IR、读 PTX、读 SASS，你都要拿它当尺子。

# 01-3 · B fragment：为什么它最别扭

上一讲我们推导了 A。A 的结论很舒服：**每个寄存器里的两个 half 在内存里是连续的**，
一次 32 位 load 就搞定。

这一讲我们看 B。B 的结论会让你有点难受：**同一个寄存器里的两个 half 在内存里不相邻**，
必须分两次读、再打包。而且这个"难受"不是我们代码写得不好，**是硬件规定的**。

更重要的是：这个别扭，正是后面 `ldmatrix.trans`、`PRMT`、甚至 `cp.async` 的
那些"怪操作"存在的根本原因。所以这一讲你务必跟到底。

## 一、B 的账：先数一遍

```
B 的元素数 = 16(K) × 8(N) = 128 个 f16
warp 线程数 = 32
每个线程 = 128 / 32 = 4 个 f16 = 2 个 .b32
```

所以 B 有 `b[0]`、`b[1]` 两个寄存器。和 A 一样，这个数字是除出来的，没有魔法。

## 二、ISA 规定的 B 布局

PTX ISA 对 `m16n8k16.row.col.f32.f16.f16.f32` 中 B 的定义（同样翻译成公式）：

```
b[0] 的低 half = B[k = 2*tig]    [n = gid]      b[0] 的高 half = B[2*tig + 1][gid]
b[1] 的低 half = B[k = 2*tig+8]  [n = gid]      b[1] 的高 half = B[2*tig + 9][gid]
```

表格版：

| 寄存器 | 第 0 个 half | 第 1 个 half |
| --- | --- | --- |
| `b[0]` | `B[k=2*tig][n=gid]` | `B[k=2*tig+1][n=gid]` |
| `b[1]` | `B[k=2*tig+8][n=gid]` | `B[k=2*tig+9][n=gid]` |

读这张表的时候，重点看**两个 half 的下标**：它们共享同一个 `n = gid`，
而 K 从 `2*tig` 变成 `2*tig+1`——**在 K 方向相邻**。

## 三、关键的一句话："同一个寄存器里，两个 half 是同一列的相邻两个 K"

把这句话和 A 对照一下：

```
A：同一个寄存器里，两个 half 是同一行相邻的两个 K     （行不变，K 相邻）
B：同一个寄存器里，两个 half 是同一列相邻的两个 K     （列不变，K 相邻）
```

看起来只是"行"和"列"换了个字。但**内存布局不同，代价完全不同**：

我们的 `B` 在 global memory 里是 **row-major**，也就是按 `B[k][n]` 存的，
`n` 方向连续。所以：

- `B[2*tig][gid]` 和 `B[2*tig+1][gid]`：**K 相邻**，在 row-major 布局里它们相差
  **N 个元素**（要跨过整整一行）。
- 而 A 的 `A[gid][2*tig]` 和 `A[gid][2*tig+1]`：**K 相邻**，在 row-major 布局里它们
  相差 **1 个元素**，连续。

画成图（假设 N=8）：

```
B 在内存里的样子（row-major，[k][n]）：

        n=0    n=1    n=2    n=3   ...   n=gid
k=0    B00    B01    B02    B03         B0g
k=1    B10    B11    B12    B13         B1g
k=2    B20    B21    B22    B23         B2g   ←  b[0] 的低 half 在这儿
k=3    B30    B31    B32    B33         B3g   ←  b[0] 的高 half 在这儿
        ↑
        这一行是连续的，但我们要的两个数在同一列、隔了一行
```

**所以 b[0] 里的两个 half 在内存里隔了 N 个元素。** 一次 `load i32` 是拿不到它们的。

## 四、源码里是怎么硬凑的

[`code/tc_mma.cu`](../../code/tc_mma.cu) 里 B 的装载：

```cpp
const int b_k0 = tig * 2, b_k1 = tig * 2 + 8;
const int b_n  = gid;                          // 输出列

const __half *pb0 = B + (k0 + b_k0) * N + tile_n + b_n;
const __half *pb1 = B + (k0 + b_k1) * N + tile_n + b_n;
b[0] = pack2_half(pb0[0], pb0[N]);   // k 2t, 2t+1 在 n 列上
b[1] = pack2_half(pb1[0], pb1[N]);   // k 2t+8, 2t+9
```

注意 `pack2_half(pb0[0], pb0[N])` 里那个 `N`：**它是"下一行的同一列"的偏移**。
也就是说，我们确实在做两件事：

1. 读 `pb0[0]`（第 2t 行、第 gid 列）；
2. 读 `pb0[N]`（第 2t+1 行、第 gid 列）——**跨了 N 个 half**；
3. 把它们拼成一个 32 位寄存器。

`pack2_half` 的实现：

```cpp
__device__ __forceinline__ uint32_t pack2_half(__half lo, __half hi) {
  __half2 h = __halves2half2(lo, hi);
  return *reinterpret_cast<uint32_t *>(&h);
}
```

`__halves2half2` 是 CUDA 提供的辅助函数。它不是"免费"的——**它会变成一条内联汇编**。
第 2 部分我们会看到它的 IR 形态：

```llvm
%7 = call i32 asm "{  mov.b32 $0, {$1,$2};}\0A", "=r,h,h"(i16 %5, i16 %6)
```

而这条 `mov.b32` 汇编**也被标了 `convergent`**（因为 CUDA 设备端的每条 asm 都被标了）。
第 2、4 部分会讲这个标记带来的连锁反应。

## 五、这一路的代价：A 一条指令，B 三条

把 A 和 B 的装载成本并排看：

```
A：1 条 ld.global.nc.b32（一次拿 2 个连续的 half）
   × 4 个寄存器 = 4 条访存

B：2 条 ld.global.nc.b16（两个不相邻的 half）
   + 1 条 mov.b32（打包）
   × 2 个寄存器 = 4 条访存 + 2 条打包
```

在 SASS 里，那条 `mov.b32` 会被 ptxas 合成一条 `PRMT`（字节置换）：

```
PRMT R24, R27, 0x5410, R29 ;
```

`0x5410` 这个立即数就是在告诉硬件"把两个 16 位拼成一个 32 位"。
第 8 部分讲 SASS 时我们会把这条指令拆开看。

**所以：B 的"别扭"最终变成了实打实的指令数。** 这就是为什么真实的 Tensor Core 代码
几乎都用 `ldmatrix`——它让硬件去做这件事，而不是靠软件拼。

## 六、这就是 `ldmatrix.trans` 存在的理由

想一想：如果我们能让硬件在"从 shared memory 装载"的时候就把这件事做了呢？

`ldmatrix` 就有这么一个变体：`ldmatrix.sync.aligned.m8n8.x2.trans.shared.b16`。
它的语义是：

- 8 个 lane 提供 8 行（K 方向）的地址；
- **装载之后按列分发**（这就是 `.trans` = transposed）；
- 于是每个 lane 拿到的就是"同一列上相邻的两个 K"——**正好是 B fragment 要的形状**。

在我们的 v2 里，B 的装载就是一条指令：

```cpp
ldmatrix_x2_trans(b, &Bs[krow][0]);   // krow = lane & 15
```

对应 PTX：

```
ldmatrix.sync.aligned.m8n8.x2.trans.shared.b16 {%r26,%r27}, [%r28];
```

**对比一下**：v1 里 B 要 4 条访存 + 2 条打包，v2 里 B 只要 1 条 `ldmatrix`。
这就是第 7 部分要展开讲的"`ldmatrix` 凭什么省事"。

但这里有个前提：**`ldmatrix.trans` 只能帮你转一次。** 我们在开发时踩过一个坑：

> 第一版我们把 B 在 shared memory 里存成 `[n][k]`（也就是搬运的时候自己转置了一遍），
> 然后又让 `ldmatrix` 去 `.trans`——**等于转了两遍，又转回来了**。
> 结果误差直接炸到 `max |D - ref| = 13.9497`。

正确做法是：**shared memory 里保持 `[k][n]` 的原始布局，让 `.trans` 去做那唯一的一次转置。**
而且 `[k][n]` 正好就是 global memory 里 B 的自然布局，`cp.async` 可以直接整行搬过来，
连手工转置的拷贝都省了。

## 七、B 的布局图（和 A 对照记忆）

```
                    n = 0..7
              ┌──────────────────────┐
   k = 0..7   │        b[0]          │   行 = 2*tig, 2*tig+1
              │  列 = gid            │   （同一列的相邻两行）
              ├──────────────────────┤
   k = 8..15  │        b[1]          │   行 = 2*tig+8, 2*tig+9
              │  列 = gid            │
              └──────────────────────┘
```

和 A 的图放在一起看，你会发现一个对称性：

```
A：上下分 K（0..7 / 8..15），左右分行      → 寄存器里两个 half 在同一行
B：上下分 K（0..7 / 8..15），整体只有一列组 → 寄存器里两个 half 在同一列
```

**A 是"行主序"的视角，B 是"列主序"的视角**——这就是指令名里那个 `.row.col` 的含义。
注意它说的是 **fragment 的逻辑组织方式**，不是你在内存里怎么存。

## 八、验证

和上一讲一样，你可以在 kernel 里打印坐标验证：

```cpp
printf("lane=%2d | b0=(k%d,n%d)(k%d,n%d)\n", lane,
       2*tig, gid, 2*tig+1, gid);
```

lane = 13（gid=3, tig=1）应该打印出 `b0=(k2,n3)(k3,n3)`——两个 half 都在第 3 列，
K 是 2 和 3。

如果你想更硬核一点，可以改一行代码验证"内存不相邻"这件事：把 `pack2_half(pb0[0], pb0[N])`
里的 `pb0[N]` 改成 `pb0[1]`，跑一遍看看误差变成多少。
（提示：`pb0[1]` 是同一行的下一列，等价于把 B 的第 2t 行和第 2t+1 行换成了第 gid 列和 gid+1 列，
结果一定会错。**这种"故意改错看误差"的做法在调试布局时非常好用。**）

## 九、小结

1. B 每线程 2 个 `.b32`（128 个 f16 ÷ 32 ÷ 2），布局是"**同一列的相邻两个 K**"。
2. 因为 B 在内存里是 row-major，这两个 half **相差 N 个元素**，
   所以必须"两次 `load i16` + 一次 `mov.b32` 打包"，SASS 里是两条 `LDG` + 一条 `PRMT`。
3. 这个别扭是硬件规定，不是代码写得不好。**`ldmatrix.trans` 就是为了让硬件替你做这件事**；
   但它只做一次转置，所以 shared memory 里要保持 `[k][n]` 原始布局。

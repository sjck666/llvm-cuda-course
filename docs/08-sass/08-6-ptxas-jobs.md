# 08-6 · ptxas 的展开与指令合成

第 8 部分最后一讲。我们把 ptxas 那些"你看不见但确实发生了"的事情列出来。

这一讲也是整门课的一个"总结点"：**它回答了"LLVM 到底把多少活留给了别人"。**

## 一、事情一：循环展开（4x + 2x + 1x）

第 04-5 讲我们留下了一个悬念：运行期 K 的那条循环，在 IR 层没展开，
**那在 SASS 里呢？**

把 `mma_tc_manual` 的控制流骨架抽出来（`tools/analyze-sass.sh`）：

```
/*01e0*/  ISETP.GT.AND P1, PT, R20, 0x30, PT ;   ; K > 48 ?
/*0290*/  @!P1 BRA 0x870 ;
[主循环 0x2c0 – 0x860]
/*0860*/  @!P1 BRA 0x2c0 ;                       ; 回到主循环（每次前进 0x40 = 4 个 k-step）
[中间循环 0x870 – 0xbd0]
/*0880*/  ISETP.GT.AND P1, PT, R12, 0x10, PT ;
/*0890*/  @!P1 BRA 0xbd0 ;
/*0b70*/  IADD3 R5, R5, 0x20, RZ ;               ; k0 += 32
[收尾 0xbd0 – 0xde0]
/*0d60*/  HMMA.16816.F32 R8, R20, R14, R8 ;      ; 最后一次累加
```

配合 HMMA 的地址分布：

```
主循环（4 条）：0x4b0  0x5f0  0x730  0x820      每轮跨过 4 个 k-step
中间循环（2 条）：0xa50  0xbb0                  每轮跨过 2 个
收尾（1 条）：0xd60                              1 个
```

**这是教科书式的 "unroll by 4 / by 2 / by 1" 分解**：任意 trip count 都能写成 `4a + 2b + c`。

`K = 64` 时走 4 次主循环 + 0 次中间 + 0 次收尾，正好 64。
`K = 48` 时走 3 次主循环（48）…… 总之不管 K 是多少都能对上。

### 这一段的三个重要认识

**认识一：ptxas 在 SASS 层做了 LLVM 没做的事。**

```
IR 层：循环没展开（因为 convergent 挡住了 runtime unroll，第 04-5 讲）
SASS 层：ptxas 把它展开了
```

**认识二：这就是为什么两个 kernel 都有 7 个 HMMA 站点。**

7 = 4 + 2 + 1 的分解结果。而源码里只有一个 `mma`（在循环里）。

**认识三：所以"IR 没展开"不等于"机器码没展开"。**

调优时你要知道自己在控制**哪一层**的展开：

```
想控制 IR/PTX 层的展开   →  写 #pragma unroll，或者调 unroll 参数
想控制 SASS 层的展开     →  只能通过 PTX 的写法间接影响（比如手工展开 PTX）
```

## 二、事情二：软件流水（把 cp.async 提前一轮）

第 08-3 讲看过：SASS 把"发起下一轮拷贝"提到了"本轮计算"之前。

```
源码：搬本轮 → 等 → 同步 → 装 → 算 → 同步
SASS：等上一轮 → 同步 → 装 → 同步 → 发起下一轮 → 提交 → 算
```

**这个优化 LLVM 做不到**（第 05-11 讲）：
因为它需要知道"异步拷贝要多久才能回来"，
而这个信息只有掌握真实硬件的 ptxas 才有。

这是"调度发生在离硬件最近的那一层"的最佳例证：

```
LLVM 侧：只能决定 PTX 里指令的书写顺序
ptxas 侧：掌握延迟模型，能重排成真正高效的顺序
```

## 三、事情三：指令合成（PTX 有、SASS 没有的东西）

对比 PTX 和 SASS，你会看到一堆 SASS 里有、PTX 里没有的指令。
挑几个最典型的：

| SASS | PTX 里对应什么 | 说明 |
| --- | --- | --- |
| `PRMT R24, R27, 0x5410, R29` | `mov.b32 %r20, {%rs1,%rs2}` | PTX 没有"拼两个 16 位"的 mov，SASS 用**字节置换**实现 |
| `IMAD.WIDE R26, R27, 0x2, R22` | `mul.wide.s32 %rd19, %r26, 2` + `add.s64` | 乘法与加法**合成一条**（乘加） |
| `CS2R R8, SRZ` | `mov.b32 %r38, 0f00000000` × 4 | 一条 `CS2R` 写两个寄存器，**清零 4 个累加器只要 2 条** |
| `IMAD.MOV.U32 R1, RZ, RZ, c[0x0][0x28]` | （PTX 里没有） | 栈指针初始化，编译器内部约定 |
| `S2R R0, SR_TID.X` | `mov.u32 %r1, %tid.x;` | 读特殊寄存器 |
| `ULDC.64 UR6, c[0x0][0x118]` | （PTX 里是直接引用参数） | 常量加载到 **uniform 寄存器** |

### `PRMT` 那条特别值得记

```
PTX:  {  mov.b32 %r20, {%rs1,%rs2};}
SASS: PRMT R24, R27, 0x5410, R29 ;
```

立即数 `0x5410` 就是一个"字节选择模式"：告诉硬件从两个源寄存器的哪些字节
拼出结果。**这正是"两个 16 位拼成一个 32 位"这件事的硬件实现。**

而它的来源，是我们在第 01-3 讲推导的"**B fragment 的两个 half 在内存里不相邻**"：

```
B 的布局别扭  →  源码里用 pack2_half 打包（第 02-7 讲）
             →  PTX 里是一条 mov.b32
             →  SASS 里是一条 PRMT
```

**从 fragment 布局一路追到 PRMT——这条链是整门课最完整的"因果链"之一。**

### `CS2R` 那条也很漂亮

PTX 里清零 4 个累加器要 4 条 `mov`，SASS 里只要 2 条 `CS2R`（每条写两个寄存器）。

**这就是"PTX 是虚拟 ISA"的含义**：PTX 允许存在语义清楚但硬件没有直接对应的指令，
ptxas 的职责之一就是把这些"理想指令"落地成真实指令。

## 四、事情四（顺带）：寄存器分配与调度

这两件事我们第 05-10、05-11 讲过了，这里只做呼应：

```
寄存器分配：PTX 里是 %r1..%r36（虚拟），SASS 里是 R0..R39（物理，40 个）
指令调度：PTX 里是源码顺序，SASS 里是 ptxas 重排后的顺序（含软件流水）
```

## 五、把"谁做了什么"列成一张表

这是整门课的一张总结表：

| 事情 | LLVM（NVPTX 后端） | ptxas |
| --- | --- | --- |
| 地址空间定性（generic → global） | ✅ | |
| kernel 参数读取方式 | ✅ | |
| 指令选择（IR → 机器指令） | ✅ | |
| PTX 寄存器命名 | ✅（per-class 编号） | |
| PHI 消除 / COPY 合并 | ✅ | |
| **寄存器分配** | ❌（不做） | ✅ |
| **循环展开（SASS 层）** | ❌ | ✅ |
| **指令调度（含软件流水）** | 部分（PTX 层顺序） | ✅（真正有效的那次） |
| **指令合成（PRMT/IMAD.WIDE…）** | ❌ | ✅ |
| **机器码编码** | ❌ | ✅ |

**一句话总结这张表：**

> **LLVM 决定"语义与结构"，ptxas 决定"物理实现"。**

理解了这条分界线，你就理解了为什么 NVPTX 后端"看起来这么薄"，
也就理解了为什么调优 GPU 代码时**必须**看 SASS 而不只是看 PTX。

```

       —— 以及"cp.async 被提前一轮"的软件流水
[08-4] HMMA 四操作数 = D/A/B/C，寄存器数 4/4/2/4，用数据流验证
[08-5] LDSM 的两个变体，以及"用不用 ldmatrix 是个取舍"
[08-6] ptxas 的四件大事：展开、软件流水、指令合成、（加上分配与调度）
```

到这里，`tc_mma.cu` 这条链就走到头了：

```
.cu → IR → 优化后 IR → MIR → PTX → SASS
```

每一层的名字、形态、负责人，你现在都能说清楚了。

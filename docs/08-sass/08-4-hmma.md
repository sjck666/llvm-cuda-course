# 08-4 · `HMMA.16816.F32` 操作数拆解

这一讲回答整门课最"硬核"的一个问题：

> **SASS 里的 `HMMA.16816.F32 R16, R16, R22, R12`，那四个寄存器分别是什么？**

## 一、格式

```
        HMMA.16816.F32   R16,        R16,        R22,       R12 ;
                         │           │           │          │
                         │           │           │          └─ Rc（C fragment，R12–R15）
                         │           │           └──────────── Rb（B fragment，R22–R23）
                         │           └──────────────────────── Ra（A fragment，R16–R19）
                         └──────────────────────────────────── Rd（D fragment，R16–R19）
```

`.16816` 就是 `m16n8k16` 的缩写（16-8-16），`.F32` 指累加器/输出的类型。

**和 PTX 一一对应**（第 07-2 讲）：

```
PTX:  mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 {D}, {A}, {B}, {C};
SASS: HMMA.16816.F32 Rd, Ra, Rb, Rc ;
```

## 二、寄存器数怎么来的

| 操作数 | 名字 | 寄存器数 | 依据 |
| --- | --- | --- | --- |
| 第 1 个 | `Rd` | 4（R16,R17,R18,R19） | D 是 16×8 f32 = 128 个 float ÷ 32 线程 = 4 |
| 第 2 个 | `Ra` | 4（R16..R19） | A 是 16×16 f16 = 256 half ÷ 32 = 8 half = 4 × b32 |
| 第 3 个 | `Rb` | 2（R22,R23） | B 是 16×8 f16 = 128 half ÷ 32 = 4 half = 2 × b32 |
| 第 4 个 | `Rc` | 4（R12..R15） | C 是 16×8 f32，同 D |

**这张表就是第 01-2 ~ 01-4 讲那三张 fragment 表在 SASS 里的样子。**

## 三、用数据流验证四个操作数的角色

光看格式不够，我们**用前后指令的数据流把它钉死**。

### 验证 Rd 和 Ra 是同一组寄存器

`Rd == Ra == R16` 看着像笔误，其实是允许的"原地覆盖"：
**A 用完就没用了，结果直接写回 A 的寄存器。**

这一轮之后 `R16–R19` 就从"A fragment"变成了"累加器"。

### 验证 Ra 确实是 A

在这条 HMMA 之前，`LDSM.16.M88.4 R16, [R4]` 正好把 4 个寄存器写进 R16–R19，
而 A fragment 就是 4 个 b32。**一条 `LDSM.x4` → 一个 `Ra`**，对得上。

### 验证 Rb 确实是 B

`LDSM.16.MT88.2 R22, [R2]` 写 R22–R23，正好 2 个寄存器，和 `Rb` 的宽度一致。

### 验证 Rc 是上一轮的累加器（最漂亮的一步）

看主循环里连续四轮的 HMMA：

```
/*0410*/  HMMA.16816.F32 R16, R16, R22, R12 ;   ; D=R16..  C=R12..
/*04f0*/  HMMA.16816.F32 R8,  R8,  R20, R16 ;   ; D=R8..   C=R16..  ← 上一轮的 D
/*05b0*/  HMMA.16816.F32 R12, R12, R22, R8 ;    ; D=R12..  C=R8..   ← 上一轮的 D
/*0630*/  HMMA.16816.F32 R12, R16, R20, R12 ;   ; D=R12..  C=R12..（原地累加）
```

**`C` 的位置上出现的，永远是上一条 HMMA 的 `D`。**

累加器在 `R12 / R16 / R8` 之间来回传递——**这就是 `D = A*B + C` 在寄存器层面的样子。**

（`Rc` 也不一定等于 `Rd`：第 4 条就是 `D=R12, C=R12`，原地累加。）

## 四、v1（手动版）里的同一件事

v1 没有 `LDSM`，A/B 都靠 `LDG` 取，但 HMMA 的形状完全一样：

```
/*03c0*/  LDG.E.CONSTANT R13, [R32.64+-0x10] ;   ┐
/*03d0*/  LDG.E.CONSTANT R12, [R30.64+-0x10] ;   │ A fragment：4 条 32 位只读加载
/*03e0*/  LDG.E.CONSTANT R14, [R30.64] ;         │  -> R12,R13,R14,R15
/*03f0*/  LDG.E.CONSTANT R15, [R32.64] ;         ┘
          ...
/*0420*/  PRMT R24, R27, 0x5410, R29 ;           ┐ B fragment：两条 16 位加载 + PRMT
/*0440*/  PRMT R25, R25, 0x5410, R35 ;           ┘  -> R24,R25
/*04b0*/  HMMA.16816.F32 R12, R12, R24, R8 ;     ; D=R12, A=R12, B=R24, C=R8
```

**这就是第 3、4 部分那些 IR 的机器码对应**：

- A 的 `load i32` × 4 → `LDG.E.CONSTANT` × 4（`.CONSTANT` 来自参数的 `readonly` 属性）；
- B 的两条 `load i16` + `mov.b32` 打包 → `LDG.E.U16.CONSTANT` × 2 + `PRMT`；
- C 的 4 个 f32 → `R8..R11`（循环前用 `CS2R` 清零）。

### fragment → SASS 寄存器映射表（v1 主循环）

| fragment | PTX 寄存器 | SASS 寄存器 | 数量 |
| --- | --- | --- | --- |
| A | `%r22..%r25` | `R12,R13,R14,R15` | 4 × b32 |
| B | `%r20,%r21` | `R24,R25` | 2 × b32 |
| C/D | `%r33..%r36` | `R8..R11` | 4 × b32 |

**请记住这张表的性质**：PTX 名字到 SASS 名字的映射是 **ptxas 在寄存器分配时决定的**，
不是 LLVM 决定的（第 05-10 讲）。换一个 `-maxrregcount`、换一个 ptxas 版本，
或者只是改一行代码，这张表就可能变。

**唯一不变的是"数量关系"**：A 占 4 个、B 占 2 个、C/D 占 4 个。

## 五、为什么这件事值得单独讲一讲

因为它是**整门课的"闭环验证"**：

```
第 01-2 ~ 01-4 讲：从 PTX ISA 的 fragment 定义，推导出 A/B/C/D 的寄存器数量与布局
第 07-2 讲：      在 PTX 里看到这四个操作数
第 08-4 讲（本讲）：在 SASS 里用数据流验证这四个操作数的角色
```

**三层对上了，说明我们对 fragment 的理解是对的。**

如果哪天你的 kernel 算错了，这套"数据流验证"也能帮你定位：

```
看 HMMA 的 Ra 是不是来自 LDSM/load 的结果？
看 Rc 是不是上一轮的 Rd？
如果 C 的位置上出现了一个奇怪的值 → 累加器布局错了 → 回去查 fragment 表
```

## 六、小结

1. `HMMA.16816.F32 Rd, Ra, Rb, Rc` 的四个操作数就是 **D / A / B / C**，
   寄存器数是 **4 / 4 / 2 / 4**——和 fragment 表的账完全一致。
2. 用数据流可以验证它们：**Ra 来自 `LDSM.x4`、Rb 来自 `LDSM.x2`、
   Rc 永远是上一条 HMMA 的 Rd**。
3. **PTX 名 → SASS 名的映射是 ptxas 决定的，会变；不变的是数量关系。**

# 07-2 · `mma.sync` 逐字段拆解

这一讲拆我们这门课的主角：

```
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
```

## 一、名字的每一段

```
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
│   │     │       │        │   │   │   │   │   └─ D 的类型：f32
│   │     │       │        │   │   │   │   └───── C 的类型：f32
│   │     │       │        │   │   │   └───────── B 的类型：f16
│   │     │       │        │   │   └───────────── A 的类型：f16
│   │     │       │        │   └───────────────── B 的布局：col（列主序）
│   │     │       │        └───────────────────── A 的布局：row（行主序）
│   │     │       └────────────────────────────── 形状：M=16, N=8, K=16
│   │     └────────────────────────────────────── aligned：warp 全 32 线程一起执行
│   └──────────────────────────────────────────── sync：warp 级同步指令
└──────────────────────────────────────────────── 矩阵乘累加
```

## 二、`sync.aligned`：这条指令"危险"的来源

**32 个线程必须同时执行到它。** 这不是性能建议，是硬件要求：
只走到一半，行为未定义。

这就是它必须被标成 `convergent` 的根本原因（第 02-6、04-6 讲）：

```
源码 asm volatile  →  IR 属性 convergent  →  MIR 标志 isconvergent
                   →  MachineSink/LICM/CSE 等一律收手
```

**一切的起点就是 `sync.aligned` 这两个词。**

## 三、`row.col`：说的是 fragment 的逻辑布局

```
.row  →  A 按"行主序"的方式组织 fragment
.col  →  B 按"列主序"的方式组织 fragment
```

**注意这说的是 fragment 的组织方式，不是内存里的存放方式。**

第 01-3 讲推导过：`.col` 意味着 B 的同一个寄存器里装的是
"同一列上相邻的两个 K"——在 row-major 内存里它们不相邻，必须分两次读再打包。
**那正是 `ldmatrix.trans` 存在的理由。**

如果你把 `row.col` 理解成"内存布局"，你会完全看不懂 B 的装载代码。

## 四、四个操作数

实测的 PTX（`dumps/03-clang-O2.ptx:106`）：

```
	mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
	    {%r33,%r34,%r35,%r36},      <- D（输出）：4 个 32 位
	    {%r22,%r23,%r24,%r25},      <- A：4 个 32 位（每个装 2 个 f16）
	    {%r20,%r21},                <- B：2 个 32 位
	    {%r33,%r34,%r35,%r36};      <- C（累加输入）：4 个 32 位
```

**D 和 C 是同一组寄存器**（`%r33..%r36` 既是输入也是输出）——
这就是 `D = A*B + C` 的"原地累加"形式（第 01-4 讲）。

和 fragment 表的对应：

| 操作数 | 寄存器数 | 每线程持有 | 对应源码 |
| --- | --- | --- | --- |
| D（第 1 个） | 4 | `D[gid][2t]`、`D[gid][2t+1]`、`D[gid+8][2t]`、`D[gid+8][2t+1]` | `float c[4]` |
| A（第 2 个） | 4 | 左上/左下/右上/右下 四个 8×8 子块 | `uint32_t a[4]` |
| B（第 3 个） | 2 | `B[2t][gid]`,`B[2t+1][gid]`；`B[2t+8][gid]`,`B[2t+9][gid]` | `uint32_t b[2]` |
| C（第 4 个） | 4 | 同 D | `float c[4]` |

## 五、为什么是 4 / 4 / 2 / 4

这个"账"值得再算一遍，因为它是判断**任何** mma 形状的通用方法：

```
A：16 × 16 = 256 个 f16  ÷ 32 线程 = 8 个 f16 = 4 个 .b32
B：16 ×  8 = 128 个 f16  ÷ 32 线程 = 4 个 f16 = 2 个 .b32
C/D：16 × 8 = 128 个 f32 ÷ 32 线程 = 4 个 f32 = 4 个寄存器
```

**"总元素数 ÷ 32" 对任何形状都成立**；需要查手册的只是"哪几个元素进哪个寄存器"。

换个形状：`m16n8k8.f16` 的 A 是 16×8 = 128 个 f16 → 每线程 4 个 f16 →
**2 个寄存器**。你会看到 PTX 里 A 的操作数从 4 个变成 2 个。

## 六、这条指令在 SASS 里是什么

第 8 部分会详细拆，这里先给对应关系：

```
PTX:  mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 {D}, {A}, {B}, {C};
SASS: HMMA.16816.F32 Rd, Ra, Rb, Rc ;
```

`16816` 就是 `m16n8k16` 的缩写（16-8-16），`.F32` 是累加器/输出类型。
**四个操作数的角色完全一样**：Rd / Ra / Rb / Rc。

## 七、一个容易记错的点：类型列表的顺序是 D-A-B-C

PTX ISA 里 type-list 的顺序是 **`Dtype.Atype.Btype.Ctype`**：

```
.f32 . f16 . f16 . f32
  D     A     B     C
```

**不是 A-B-C-D。** 这是个很容易读反的细节：你如果按"先输入后输出"的直觉读，
就会把四个类型全搞错。

（另外还有一种简写形式：某些变体的类型列表可以省略一部分，
这就是为什么 NVVM intrinsic 名字里会出现 `...f32.f32` 这种只有两个类型的写法——
第 09-3 讲会讲这个坑。）

## 八、小结

1. `mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32` 的每一段都在说一件明确的事：
   **谁参与、怎么布局、什么类型、什么规模**；其中 `sync.aligned` 就是 `convergent` 的根源。
2. 四个操作数是 **D / A / B / C**，寄存器数 **4 / 4 / 2 / 4**，
   用"总元素数 ÷ 32 ÷ 每寄存器元素数"就能算出来。
3. 类型列表顺序是 **D-A-B-C**，别按直觉读成 A-B-C-D。

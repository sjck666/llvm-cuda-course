# 07-3 · `ldmatrix` 精讲

第 01-3 讲留下了一个悬念：**B fragment 的布局很别扭（同一个寄存器里两个 half 不相邻），
所以 v1 版本要"两次 `ld.global.nc.b16` + 一次打包"。**

`ldmatrix` 就是为了解决这类问题而存在的。这一讲把它讲透。

## 一、它的语义

```
ldmatrix.sync.aligned.m8n8.x4.shared.b16 {%r1,%r2,%r3,%r4}, [addr];
```

| 字段 | 含义 |
| --- | --- |
| `ldmatrix` | Load Matrix：**按矩阵布局分发**的批量加载 |
| `.sync.aligned` | warp 级同步（和 mma 一样） |
| `.m8n8` | 每个"小矩阵"是 8×8 |
| `.x1` / `.x2` / `.x4` | 加载 1 / 2 / 4 个这样的矩阵 |
| `.trans` | 转置：装载后按转置的方式分发 |
| `.shared` | 源地址在共享内存 |
| `.b16` | 元素 16 位 |

**关键认识：它不是普通的"批量加载"。**

> **它的输出天然就是 mma 需要的 fragment 布局。**

普通的 `ld.shared` 只能给你"连续的一串数据"；
而 `ldmatrix` 会**按 fragment 的规则分发到 32 个线程**。这才是它存在的理由。

## 二、地址怎么给：每 8 个 lane 给一个矩阵的 8 行地址

```
lane 0–7   提供第 1 个矩阵的 8 行地址
lane 8–15  提供第 2 个矩阵的 8 行地址   （.x2 及以上）
lane 16–23 提供第 3 个矩阵的 8 行地址   （.x4）
lane 24–31 提供第 4 个矩阵的 8 行地址   （.x4）
```

每个 lane 给出**一行的起始地址**，硬件负责把这一行的 8 个元素分发给该拿它的线程。

所以 `.x4` 需要 **32 个 lane 全部参与**——这也是它必须 `convergent` 的原因。

## 三、我们的 A：`ldmatrix.x4`，地址顺序要小心

A 是 16×16，正好四个 8×8 子块（第 01-2 讲的图）：

```
        k=0..7      k=8..15
row0-7  [ 矩阵0 ]   [ 矩阵2 ]
row8-15 [ 矩阵1 ]   [ 矩阵3 ]
```

而 mma 的 A fragment 寄存器顺序是：

```
a[0] = 左上    a[1] = 左下    a[2] = 右上    a[3] = 右下
```

**是"先上下、后左右"，不是"先左右、后上下"。**

所以给 `ldmatrix.x4` 的地址顺序必须是：

```
lane 0–7   → 矩阵0（左上）
lane 8–15  → 矩阵1（左下）
lane 16–23 → 矩阵2（右上）
lane 24–31 → 矩阵3（右下）
```

源码里那段别扭的计算就是干这个的：

```cpp
const int grp  = lane >> 3;                          // 0..3 → 对应哪个矩阵
const int arow = (lane & 7) + ((grp & 1) ? 8 : 0);   // grp 奇数 → 下半
const int acol = (grp >= 2) ? 8 : 0;                 // grp >= 2 → 右半
ldmatrix_x4(a, &As[arow][acol]);
```

```
grp&1   决定行偏移（0-7 还是 8-15）
grp>=2  决定列偏移（k 是 0-7 还是 8-15）
```

**很多人第一次写 `ldmatrix.x4` 会按"先列后行"排地址，结果 `a[1]` 和 `a[2]` 装反。**

## 四、我们的 B：`ldmatrix.x2.trans`，以及那次翻车

B 是 16×8，分成两个 8×8 块。每个 lane 需要拿到**同一列 n=gid 上相邻的两个 k**。

共享内存里 `Bs` 按 `[k][n]` 行主序存（这是 B 在 global 里的自然布局）：

```cpp
const int krow = lane & 15;      // lane 0-15 分别指向 k=0..15 的行首
ldmatrix_x2_trans(b, &Bs[krow][0]);
```

`.trans` 的语义是：**把"按行分发"变成"按列分发"**。
装载时 8 个 lane 给的是 **k 行**地址，转置之后每个 lane 拿到的是
**同一列上相邻的两个 k**——正是 B fragment 要的。

### 我们翻过的车：转置了两遍

第一版我们在**搬进共享内存时手动转置了一遍**（存成 `[n][k]`），
然后又让 `ldmatrix` 去 `.trans`——**等于转了两遍，又转回来了**。

结果：

```
[v2 ldmatrix] max |D - ref| = 13.9497   -> FAIL
```

误差从 `1e-6` 量级直接炸到 `13.9`。**这不是精度问题，是布局错了。**
改成 `[k][n]` 自然布局之后立刻 PASS。

教训：

> **`ldmatrix.trans` 已经帮你转了一次，共享内存里就存原始布局。**

而且 `[k][n]` 正好是 B 在 global 里的自然布局，`cp.async` 可以整行搬过来，
连手工转置的拷贝都省了。

## 五、实测的三条指令

```
	ldmatrix.sync.aligned.m8n8.x4.shared.b16 {%r21,%r22,%r23,%r24}, [%r25];
	ldmatrix.sync.aligned.m8n8.x2.trans.shared.b16 {%r26,%r27}, [%r28];
	mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 {%r38,%r39,%r40,%r41}, {%r21,%r22,%r23,%r24}, {%r26,%r27}, {%r38,%r39,%r40,%r41};
```

**看操作数**：`ldmatrix.x4` 的输出 `{%r21,%r22,%r23,%r24}` **原封不动**成了
`mma` 的 A 操作数；`ldmatrix.x2.trans` 的输出 `{%r26,%r27}` 成了 B。

**中间没有任何搬运指令。** 对比 v1：

```
A：4 条 ld.global.nc.b32
B：2 条 ld.global.nc.b16 + 一次 mov.b32 打包
```

**v2 里 A 和 B 各只要一条 `ldmatrix`。**

## 六、地址是怎么算出来的

`[%r25]` / `[%r28]` 是**共享内存的 32 位偏移**，来自：

```
	mov.b64 	%rd9, _ZZ15mma_tc_ldmatrixE2As;   ; 共享内存符号基址
	add.s64 	%rd10, %rd9, %rd8;                ; + 偏移
	mul.wide.u32 	%rd11, %r11, 2;
	add.s64 	%rd12, %rd10, %rd11;
	cvt.u32.u64 	%r19, %rd12;                 ; 64 位地址 → 32 位偏移
```

**最后那一步 `cvt.u32.u64` 就是 `__cvta_generic_to_shared` 的真身**
（第 02-3 讲）：sm_89 上共享内存本来就是"32 位偏移"寻址。

## 七、小结

1. `ldmatrix` **不是普通批量加载**，输出**天然就是 fragment 布局**——这是它存在的理由。
2. 地址由**每 8 个 lane 给一个 8×8 矩阵的 8 行地址**；`x4` 需要 32 lane 全参与。
   **A 的地址顺序必须是"左上、左下、右上、右下"**（对应 `a[0..3]`）。
3. `.trans` 只转一次：**共享内存保持 `[k][n]` 原始布局**，
   否则误差会炸到 `13.9` 那个量级。

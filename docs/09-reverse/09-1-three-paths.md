# 09-1 · 三条路线与"规格化"

动手之前，先想清楚两件事：**走哪条路**，以及**把指令翻译成编译器要的什么信息**。

## 一、三条路线

| 路径 | 要不要改编译器 | 谁能用 | 我们案例里的例子 |
| --- | --- | --- | --- |
| **A. inline asm** | 不改 | CUDA C++ 程序员 | `code/tc_mma.cu`（第 1–8 部分全在讲它） |
| **B. 现成的 LLVM IR intrinsic** | 不改（但要写 IR） | 手写 IR 的人、其他前端、MLIR 后端 | 第 09-3 节的 demo |
| **C. 新增 intrinsic + pattern** | 改 LLVM 源码 | 编译器工程师 | 第 09-2 节的六步法 |

### 怎么选

```
你要在 .cu 里手写 kernel 吗？
  ├─ 是 → 走 A（inline asm）。写完直接用，
  │        代价是优化器不认识这段汇编（第 04-6 讲的 convergent 连锁反应）
  └─ 否 → 你要让"某个上游"自动生成这条指令吗？
           ├─ 是 → 走 C（或者用别人已经加好的 intrinsic 走 B）
           └─ 否 → 走 B，手写 IR 调 intrinsic
```

### 一个必须知道的事实

**在我们的环境里，CUDA 的 `mma` / `ldmatrix` 没有 clang 内建函数**
（没有 `__nvvm_mma_m16n8k16_*` 这种 builtin；clang 的 NVPTX builtin 表里
有的是 `__hmma_*` 那批老的 wmma 系列，见第 09-2 节）。

所以 CUDA C++ 用户只有两条路：

```
1. 写 inline asm（这就是为什么 CUDA 世界里的手写 kernel 清一色是 asm volatile）
2. 自己写 IR，调 intrinsic（第 09-3 节）
```

## 二、"规格化"：把手册上的一行翻译成编译器要的六件事

不管走哪条路，你都得先把这条指令"翻译"成编译器能理解的信息。以我们的
`mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32` 为例：

| # | 项目 | 内容 |
| --- | --- | --- |
| 1 | **语义** | `D = A × B + C`，warp 级 |
| 2 | **形状** | M=16, N=8, K=16 |
| 3 | **操作数类型与数量** | A: 16×16 f16；B: 16×8 f16；C/D: 16×8 f32 |
| 4 | **寄存器类** | A/B 用 32 位寄存器（打包 2 个 f16），C/D 用 32 位浮点 |
| 5 | **内存与副作用** | 不访问内存；但会隐式影响 warp 状态 |
| 6 | **收敛性** | **是**（warp 必须一起执行） |

第 3、4 项算出来就是 **A=4、B=2、C=D=4**（第 01-2 ~ 01-4 讲的"每线程寄存器数 = 总元素数 ÷ 32"）。

### 第 6 项最重要

**如果漏了"收敛性"这一条，你会得到"大部分时候对、偶尔错"的 kernel**——
这是最难查的一类 bug，因为：

```
编译器不知道它是收敛操作 → 允许把它搬进条件分支/复制它
                      → 某些 warp 只执行了一部分
                      → 硬件行为未定义（轻则结果错，重则死锁）
```

这就是第 02-6 讲那条 `convergent` 属性存在的理由，也是第 04-6 讲
那些 pass"见到它就收手"的原因。

## 三、路线 A 的实现清单（我们全程验证过）

如果你选 inline asm，需要做四件事：

1. **写约束**：`"=f,=f,=f,=f,r,r,r,r,r,r,f,f,f,f"`——4 输出 + 10 输入
   （第 02-6 讲逐项对照过）；
2. **接受 convergent**：CUDA 设备端的所有 asm 都会被标 convergent，
   想摘掉只有两条路（第 02-6、04-6 讲实测过四条）；
3. **管理 fragment 布局**：A/B/C/D 四张表（第 01-2 ~ 01-4 讲），
   错了就是 `max |D-ref| = 13.9` 那种量级的错；
4. **验证到底层**：PTX 里确认指令出来了（第 7 部分）、
   SASS 里确认 `HMMA` 的操作数符合预期（第 8 部分）。

**结论：路线 A 不用动 LLVM 一行代码，但你要自己承担布局、对齐、收敛性三件事。**

## 四、路线 C 的六步法（下一讲展开）

如果目标是"让 LLVM 自己生成这条指令"，流程是六步：

```
1. intrinsic 定义        llvm/include/llvm/IR/IntrinsicsNVVM.td
2. 机器指令 + pattern    llvm/lib/Target/NVPTX/NVPTXIntrinsics.td
3. 内存行为登记          llvm/lib/Target/NVPTX/NVPTXISelLowering.cpp
4. 前端 builtin（可选）  clang/include/clang/Basic/BuiltinsNVPTX.td
5. 测试                  llvm/test/CodeGen/NVPTX/...
6. 三段验证              llc → ptxas → 上机对拍
```

**这六步的顺序不是随意的**：每一步都依赖前一步（没有 intrinsic 就没法写 pattern，
没有 pattern 就没法验证），而且**每一步都有"必须写对、否则后面全白干"的关键点**
（比如第 1 步的 `IntrConvergent`）。

## 五、小结

1. 三条路线：**inline asm**（不改编译器）、**现成 intrinsic**（写 IR）、
   **新增 intrinsic + pattern**（改 LLVM 源码）；选择依据是"谁生成这条指令"。
2. 不管走哪条路，先把指令**规格化成六件事**；其中**"收敛性"最容易被漏、
   后果最严重**。
3. 这六件事会分别落到 `.td` 的 intrinsic 定义、指令定义、内存行为登记、
   前端 builtin 和测试里——这就是下一讲的六步法。

## 六、动手题

1. 挑一条你熟悉的 PTX 指令（比如 `shfl.sync`、`redux.sync`），
   把它的"六件事"写出来。**你会发现第 6 件（收敛性）常常需要查文档才能确定。**
2. 想一想：如果让你给 `wgmma`（sm_90 的 warpgroup MMA）写后端支持，
   这"六件事"里哪几件会变得很不一样？（提示：它不再是"每线程持 fragment"，
   而是"操作数放共享内存 + 描述符"。）

# 04-3 · InstCombine：优化器的小账本

上一讲的 SROA + mem2reg 把 796 行砍到 353 行。这一讲看接下来那一刀：
**InstCombine 把 353 行砍到 338 行**（`16-after-instcombine.ll`）。

只有 15 行，但每一行都是"小账本"级别的改写——**而它们往往决定 SASS 里少不少一条指令**。

## 一、这个 pass 是干什么的

InstCombine 是 LLVM 里最"碎"的 pass。它专门做**指令级别的代数化简**，
比如：

```
(x & 3) * 2       →  (x * 2) & 6
x * 2             →  x << 1
x + 0             →  x
(a | b) & a       →  a
x < 0 && x > -1   →  false
```

它跑很多遍（流水线里出现 9 次），每次修一点。所以你在 IR 里看到"莫名其妙的写法"时，
第一反应应该是：**这是 InstCombine 改出来的**。

## 二、我们案例里最典型的两处

在 `dumps/02-device-O2.ll` 的准备块里：

```llvm
  %12 = lshr i32 %7, 2               ; gid = lane >> 2
  %14 = shl nuw nsw i32 %7, 1        ; lane * 2   ← 注意这里的 nuw nsw
  %15 = and i32 %14, 6               ; (lane * 2) & 6
  %16 = or disjoint i32 %15, 8       ; (lane * 2) & 6 | 8
```

而你在源码里写的是：

```cpp
const int gid = lane >> 2;      // %12
const int tig = lane & 3;       // ← 没有单独的 and 了
const int a_c0 = tig * 2;       // %15 的来历
const int a_c1 = tig * 2 + 8;   // %16
```

### 改写一：`(lane & 3) * 2` → `(lane * 2) & 6`

你写的是"先取低两位，再乘 2"。InstCombine 看到乘法是 2 的幂，就把它变成移位，
并且**把掩码提到移位之后**：

```
(lane & 3) * 2   ==   (lane << 1) & 6   ==   (lane * 2) & 6
```

为什么这样更好？因为 `& 6` 这个常量比 `& 3` 更容易和后面的地址计算合并
（它是"字节偏移"级别的掩码）。**看起来只是换了写法，但 SASS 上可能少一条 `LOP3`。**

### 改写二：`lane >> 2` 从 `ashr` 变成 `lshr`

源码里 `lane` 是 `int`，`lane >> 2` 按 C 语义是**算术**右移（`ashr`）。
但 `ValueTracking` 能推出 `threadIdx.x` 的取值范围是 `0..1023`（非负），
于是带符号的算术右移可以降级成**逻辑**右移 `lshr`。

`lshr` 的语义比 `ashr` 弱，"承诺更少"，所以后端能做的事更多
（比如可以直接用一条逻辑移位指令）。

**这一处改动值得特别注意**：它说明优化器不只是"改写表达式"，
它还在**主动推断变量的取值范围**。这也是为什么同样一行 C 代码，
在不同上下文里可能编译出不同的 IR。

### 改写三：那些 `nuw` / `nsw`

```llvm
  %14 = shl nuw nsw i32 %7, 1
  %13 = add nuw nsw i32 %12, 8
```

`nuw`（no unsigned wrap）和 `nsw`（no signed wrap）是"**不会溢出**"的承诺。
它们不是装饰：后端可以据此把两条算术合成一条 `IADD3`，或者直接用有限位宽算地址。

它们同样是 InstCombine / ValueTracking 推出来的。源码里 `%`、`&` 写得越"干净"，
这类标记就越多——**这也是手写 kernel 时值得注意的一个习惯**。

## 三、`or disjoint`：一个很实用的提示

```llvm
  %16 = or disjoint i32 %15, 8
```

`disjoint` 的意思是"两个操作数的置位区间不重叠"，所以这个 `or` 不会产生进位——
**等价于加法**。

为什么有用？因为地址计算最喜欢加法。有了这个提示，后端可以把
`or` 直接折进 `IADD3` 或者寻址模式里，而不是老老实实做一次逻辑或。

在我们循环里还有一处更有意思的：

```llvm
  %75 = or disjoint i32 %59, %15      ; k0 + tig*2
```

`%59` 是 `k0`（16 的倍数，低 4 位为 0），`%15` 是 `tig*2`（小于 16）。
两者低位不重叠，所以 `or` 等价于 `add`——前端用 `or` 表达"这里没有进位"。

**你写的是 `k0 + tig * 2`，编译器发现两部分的位域不重叠，于是用 `or disjoint` 记下这个事实。**

## 四、自己动手看 InstCombine 干了什么

最方便的办法是"只跑这一个 pass，然后 diff"：

```bash
opt -passes='instcombine' -S dumps/15-after-sroa-mem2reg.ll -o - \
  | diff - dumps/15-after-sroa-mem2reg.ll | head -40
```

你会看到一堆 `-` / `+` 行，每一对都是一个小改写。
**这是学 InstCombine 最快的方式**：不是去读它的源码（那有上万行），
而是拿自己的代码喂给它，看它改了什么。

## 五、小结

1. InstCombine 做的是**指令级代数化简**，它解释了很多"我明明没这么写"的 IR 写法。
2. 我们案例里的三处典型：`(lane&3)*2` → `(lane*2)&6`、
   `ashr` → `lshr`（借助取值范围推断）、`or disjoint`（无进位提示）。
3. 这些改写看着琐碎，但它们决定**后端能不能把地址计算折进一条指令**。
   读 IR 时看到奇怪的写法，先想"这是不是 InstCombine 干的"。

## 六、动手题

1. 跑一遍上面的 `diff`，找出三条你能看懂的改写，说说它们分别省了什么。
2. 挑战题：`%15 = and i32 %14, 6` 里那个 `6` 是怎么来的？
   （提示：`tig = lane & 3`，乘 2 之后取值范围是 `0,2,4,6`——
   用二进制写出来就知道为什么掩码是 `110` 了。）
